# 01. System overview

## What LevelUp DSA is

A Flask web application that helps IT engineering students decide which career path to aim for and then practise for
it. Full name used in the README: *LevelUp DSA: Personalized Career Intelligence System with Gamified Scenario
Practice for Students Interested in the IT Sector.* It is aimed at students at tier 2 / tier 3 engineering colleges who
have little access to structured career mentoring.

## The problem (four gaps)

1. No structured career direction: students study randomly without knowing what the industry wants.
2. No clear skill-gap awareness: students do not know what they are missing for a target role.
3. Practice disconnected from real work: algorithm drills say little about the decisions a job involves.
4. No single measure of placement readiness.

## How each part answers a gap

| Gap | Feature |
|---|---|
| Direction | Adaptive career quiz ranks 15 IT paths; Goals page; personalised roadmap |
| Skill gaps | Resume analyzer compares the student's resume skills with what the target path needs |
| Disconnected practice | 75 workplace scenarios (5 per path) that end with a real coding question |
| Readiness | One 0-100 placement readiness score, "ready" at 70 |
| Motivation (supporting) | XP, 7 levels, streak, 14 badges (no leaderboard, by design) |

## The student journey (end to end)

1. **Sign up / log in** (username or email + password).
2. **Career quiz**: 8 to 14 adaptive questions from a bank of 18 → ranked list of the 15 paths with a confidence
   score each. Ties are shown as ties.
3. **Goals**: three short questions (what to avoid, target company type, main goal) + optional note. They do **not**
   change the match. They tailor coding problems, which scenarios are starred, and the roadmap's personal note.
4. **Pick a path**: the student chooses any of the 15 (the top quiz matches are marked; if several tie, the student chooses).
5. **Roadmap**: a reviewed step-by-step roadmap for that path, personalised with one short LLM call; progress is
   tracked step by step. Videos/resources are found per step.
6. **Resume analyzer**: upload a PDF → extracted skills, resume score, ATS-style score, skill gaps vs the target path,
   live job listings, LLM feedback.
7. **Scenarios**: a game-style level map for the path. A level unlocks when the previous one is passed (70%+). Each
   scenario has decision questions and ends with a coding question on an online-assessment style screen.
8. **Dashboard / Profile**: level, XP, streak, badges, readiness score, saved results, personal details.

## Architecture in one picture (describe this as a diagram in the report)

```
Browser (HTML + CSS + vanilla JS, Jinja2 templates, no build step)
   │  JSON over HTTPS-style requests, CSRF token on every state-changing request
   ▼
Flask app  (app/__init__.py: create_app)
   ├─ routes/      thin HTTP layer: auth, quiz, conversation (Goals), roadmap, resume,
   │               scenarios, gamification, readiness, dashboard, profile, career paths
   ├─ pipeline/    the logic: quiz engine, Goals + profile builder, roadmap generation,
   │               resume extraction/gap/ATS, scenario + code engines, gamification, readiness
   ├─ models.py    SQLAlchemy tables  ──►  PostgreSQL
   └─ llm layer    one client, three providers: Gemini (default), Amazon Bedrock, any OpenAI-compatible API
Local data files:  data/scenarios/*.json (15), data/base_roadmaps/*.json (15), FAISS knowledge base (5,115 chunks)
External services: OneCompiler (run code), Adzuna (job listings), YouTube Data API (videos), the LLM provider
```

## Technology choices and the reason for each

| Choice | Why |
|---|---|
| Flask + SQLAlchemy + PostgreSQL | Simple, well-known stack; PostgreSQL for real relational data and JSON columns |
| Vanilla JavaScript, no framework or build | Keeps the project small and runnable by anyone; all dynamic text is set with `textContent` (no `innerHTML`), which removes a class of XSS bugs; a test greps for it |
| FAISS + all-MiniLM-L6-v2 | Local semantic search over the roadmap knowledge base without a paid service |
| spaCy PhraseMatcher + pdfplumber | Deterministic skill extraction from resumes (explainable, no model call) |
| LLM used sparingly | Only for roadmap personalisation (one short call) and resume feedback; content that must be correct (scenarios, problems, base roadmaps) is authored and reviewed, then validated by scripts |
| Hidden tests run on the server | The browser never receives hidden test inputs; code runs in OneCompiler, not on the app server |
| Level unlock enforced on the server | `scenario_locked` (HTTP 403) so it cannot be bypassed from the browser |
| Server-side grading | The whole attempt is graded on the server; the browser only sends answers |

## Where the knowledge base and content came from

- Roadmap knowledge base: roadmap.sh content, Stack Overflow Developer Survey 2025, an India job-market dataset.
- Scenarios, scenario questions, coding problems: authored for the project, then checked by a validator and a
  blind-solve checker (see file 04). 
- Base roadmaps: reviewed JSON files, one per path. One (Cybersecurity) was produced by a different, smaller model;
  see file 03, section 1, and file 04.

## Status

Feature-complete and tested locally. **Not deployed.** No real-user study has been run.

# 02. Feature guide

For each feature: what the student sees, what happens behind it, the key design decisions, and where the code is.
Exact route lists and file sizes are in file 03. Full detail and history: `docs/DEV_SETUP.md` (how it works) and
`docs/PROJECT_BIOGRAPHY.md` (decisions and what was verified).

## 1. Accounts and profile
- **Student sees:** signup (username, email, password), login with username *or* email, show-password toggle, a profile page
  (personal details, profile picture, change password).
- **Behind it:** passwords hashed with bcrypt; Flask-Login sessions; CSRF token on every state-changing request;
  login/password-change rate limits; the profile picture is re-encoded to a 256x256 JPEG (Pillow), so uploaded files are
  never served as-is. After a server restart in development, everyone is logged out (`LOGOUT_ON_RESTART`, a per-start
  `BOOT_ID` stamped on the session at login) because the session cookie is signed and would otherwise survive a restart.
  In production this is off because several workers have different boot ids.
- **Code:** `app/routes/auth.py`, `app/routes/profile.py`, `app/models.py`, `app/__init__.py`.

## 2. Career quiz
- **Student sees:** one question at a time (8 to 14 asked from a bank of 18), then a ranked list of the 15 paths with a
  confidence score each. Tied top paths are shown together as "Your top matches".
- **Behind it:** every answer option signals 1 to 3 career paths; the engine adds up signals, picks the next question
  that best separates the leading paths (a variance proxy; pair-aware for look-alike paths such as Data Science vs Data
  Analytics), and stops early only when the leader is clearly ahead (never before 8 answers, always at 14).
- **Important honesty:** the option-to-path signals are **hand-authored judgement**, not learned from data. The quiz is
  tested for consistency (same answers give same result; opposite answers give opposite results), not for accuracy.
- **Code:** `app/pipeline/career_quiz_data.py` (questions + signals), `career_quiz_engine.py`, `career_path_registry.py`,
  `app/routes/quiz.py`, `docs/QUIZ_QUESTION_BANK.md` (all questions in readable form).

## 3. Goals ("Personalise your plan")
- **Student sees:** three short questions (what to avoid, target company type, main goal) and an optional note, then a
  summary of exactly what was tailored.
- **Behind it:** answers are saved with the quiz result as the career profile. They do **not** change the career match.
  They (a) pick which coding problem variants a student gets, (b) star recommended scenarios, (c) add a personal note to
  the roadmap. The numbering of the questions starts at C2 because an unused question (C1) was removed on purpose.
- **Code:** `app/pipeline/conversation_data.py`, `conversation_engine.py`, `goal_tailoring.py`, `profile_builder.py`,
  `app/routes/conversation.py`.

## 4. Roadmap
- **Student sees:** a phased, step-by-step roadmap for the chosen path, a progress bar, tick boxes per step, videos and
  resources per step, a "complete" moment at 100%, and a list of earlier roadmaps.
- **Behind it:** two modes. (1) *Cached base roadmap* (default): one reviewed JSON file per path (15), personalised with
  one short LLM call that writes the personal note. Fast and predictable. (2) *Full generation*: retrieval from the FAISS
  knowledge base (5,115 chunks, all-MiniLM-L6-v2) plus an LLM call writes a roadmap from scratch, run as a background job.
  Videos come from a knowledge-base-first resolver, with YouTube search as fallback.
- **Code:** `app/pipeline/` roadmap modules, `data/base_roadmaps/`, `app/routes/roadmap.py`; DEV_SETUP sections
  "Background roadmap generation" and "Base roadmaps (cached mode)".

## 5. Resume analyzer
- **Student sees:** upload a PDF and choose a target path (or ask which path fits the resume). Results: skills found,
  skills missing for the target, a resume score, an ATS-style score with reasons, live job listings with a median
  salary, and written feedback.
- **Behind it:** pdfplumber reads the text; a spaCy PhraseMatcher finds skills from a curated skill list (with aliases
  and implied skills, e.g. a framework implies its language); gap analysis compares with the path's required skills;
  Adzuna supplies live listings; one LLM call writes feedback. Skill extraction is deterministic and explainable.
- **Code:** `app/pipeline/` resume modules, `app/routes/resume.py`; BIOGRAPHY sections "Phase 2", "Resume Modes",
  "Resume Fixes", "Lightweight ATS Score".

## 6. Scenarios
- **Student sees:** a game-style level map for the path: 5 levels, each unlocked only after the previous is passed (70%
  or more), with best score and a recommended next one. A scenario is a short workplace situation with decision
  questions (multiple choice and similar), then a coding question.
- **Behind it:** 75 scenarios (5 per path), 340 questions, authored as JSON and checked by a validator and a blind-solve
  checker. An attempt is created on the server with a shuffle seed; answers are saved as they come; the **whole attempt
  is graded on the server**. The unlock rule is enforced server-side (HTTP 403 `scenario_locked`).
- **Code:** `data/scenarios/*.json`, `app/pipeline/` scenario modules, `app/routes/scenarios.py`,
  `app/static/js/scenarios.js`; DEV_SETUP section "Scenarios".

## 7. Coding questions (inside scenarios)
- **Student sees:** an online-assessment screen. Problem on the left; right side has a language picker (Python, C++,
  Java, JavaScript), an editor and tabs for test cases and results. **Run** tests the code against all tests as often as
  wanted (visible tests show input/output; hidden tests show only "a of b passed"). **Submit** locks the answer.
- **Behind it:** 120 problems (8 per path) in 360 variants; the variant a student gets depends on their goal. Code is
  executed by the OneCompiler API (not on the app server). Hidden test inputs never leave the server. Each Run costs
  roughly one OneCompiler credit per test.
- **Code:** `data/scenarios/*.json` (`code_pool`), code runner module in `app/pipeline/`, `app/routes/scenarios.py`
  (`code_run`); DEV_SETUP section "Code questions". Runner modes: `onecompiler` (real), `local` (laptop only, not a
  sandbox), `fake` (tests).

## 8. Gamification
- **Student sees:** level card (Intern to Principal Engineer), XP, daily streak, 14 badges with progress, and a reward
  card after each submitted scenario. No leaderboard, on purpose.
- **Behind it:** nothing is stored; every number is recomputed from submitted attempts and ticked roadmap steps, so it
  cannot drift. XP: 10 per correct question (best attempt per scenario), +20 first pass, +10 for a 100% scenario, +15
  per distinct coding problem solved, +5 per ticked roadmap step. Retrying cannot farm XP.
- **Code:** `app/pipeline/gamification.py`, `app/routes/gamification.py`, `app/static/js/gamification.js`.

## 9. Placement readiness score
- **Student sees:** one 0-100 score on the dashboard with its four parts; "placement ready" at 70.
- **Behind it:** weights roadmap progress 25%, skill match 35%, scenario results 30%, 30-day activity streak 10%. If a
  part is unavailable (for example no scenario file for a path) it is dropped and the others are re-scaled. "Ready" is
  decided on the unrounded score.
- **Honesty:** the weights are a design choice, not derived from data; the score has not been checked against real
  placements.
- **Code:** `app/pipeline/readiness.py`, `app/routes/readiness.py`.

## 10. Dashboard
Shows the saved quiz result, roadmap progress, resume summary, scenarios, level, badges and readiness in one place.
`app/routes/dashboard.py`, `app/static/js/dashboard.js`.

## Cross-cutting
- **LLM layer:** one client, three providers (Gemini default; Amazon Bedrock optional; any OpenAI-compatible API).
- **Security basics:** CSRF on every state-changing request, no `innerHTML`, bcrypt, rate limits, signed cookies,
  server-side grading and unlock checks. `smoke_test_security.py` checks these.
- **Front-end design system:** CSS tokens in `:root`, shared components, no web fonts; see DEV_SETUP "Front-end design system".

# 04. Verification and limits

Write the evaluation and limitations chapters from this file. Do not add claims that are not here.

## What was tested

Eight automated smoke-test suites run against a real PostgreSQL database. They do not call paid services (code
execution is faked or run locally). Expected results on the project owner's machine:

| `smoke_test_code_questions.py` | 198 | Coding screen backend, Run vs Submit, hidden-test secrecy, languages |

| `smoke_test_gamification.py` | 49 | XP, levels, streak, badges |
| `smoke_test_readiness.py` | 70 (69 without the survey table) | Readiness score |
| `smoke_test_quiz.py` | 33 | Quiz engine, golden-file replay of 30 seeded runs, opposite-persona check |

Total 795 checks (794 on a database without the survey table). Run command is in the README.

Also done: content validators and a blind-solve checker for scenarios; a UI review by running the real pages in a browser (Chromium) and checking
screenshots; written reviews of scenario content for Cybersecurity and Data Science (`docs/SCENARIO_REVIEW_*.md`).

## What was NOT verified (state this plainly in the report)

- **Quiz accuracy.** Option-to-path signals are hand-authored judgement. There is no study comparing results with real
  students' outcomes or with a counsellor. Consistency is tested; correctness is not measured.
- **Readiness weights** (25/35/30/10) are a design choice with no data behind them.
- **No real-user testing**: no usability study, no survey results, no user counts.
- **C++ and Java through OneCompiler** have not been confirmed end to end (file names and runtime behaviour); the
  development laptop has no C++/Java toolchain. Python and JavaScript are the confirmed ones.
- **Browsers:** checked in Chromium. Other browsers and the OS "reduce motion" setting were not checked.
- **Restart-logout** is unit-tested with simulated restarts, not confirmed in a real browser session.
- **Deployment:** none. Production settings exist in code but have never run on a server. Mobile layout was not a goal.
- **Cybersecurity base roadmap** was generated by a smaller model (`openai/gpt-oss-20b`) than the others
  (`claude-opus-5-5`), has fewer phases (2) and was reviewed but is the weakest of the 15.
- The LLM-written parts (roadmap personal note, resume feedback) depend on the provider and key; they were checked on
  samples, not exhaustively.

## Honest limitations (for the "Limitations and future work" chapter)

1. Quiz validity is unproven (above); future work: classmate top-3 survey, expert review, grounding in an established
   interest model such as Holland RIASEC, archetype persona tests.
2. Content is authored and fixed: 15 paths, 5 scenarios each. Adding a path means authoring a scenario file, problems,
   a base roadmap and quiz signals.
3. Code execution depends on a third-party API with per-test cost and limits.
4. Resume skill extraction relies on a curated skill list; unlisted skills are not found.
5. No migrations tool: schema changes are done with `db.create_all` and one-off scripts.
6. Single-language UI (English), no accessibility audit beyond basic checks.
7. Not deployed; no monitoring, backups or load testing.

## Future work that was discussed but NOT built (label it "idea", never "done")

- A chat-style quiz using an LLM to extract evidence, with code validating the scores and the classic quiz as fallback.
- Deployment with several workers and `LOGOUT_ON_RESTART` off.
- A classmate survey to check the quiz.

# 07. Glossary and FAQ

## Glossary

| Term | Meaning in this project |
|---|---|
| Career path | One of 15 IT career directions the quiz ranks (list in file 03) |
| Confidence score | A per-path percentage from the quiz engine; a relative ranking, not a probability of success |
| Goals | Three questions after the quiz that tailor practice and the roadmap but do not change the match |
| Roadmap | Phased list of steps to learn for a path; base roadmaps are reviewed JSON files |
| Base roadmap | The reviewed, cached roadmap for a path, personalised by one short LLM call |
| RAG | Retrieval-augmented generation: retrieve relevant text from the knowledge base, then have an LLM write from it |
| FAISS | Library for fast similarity search over vectors; here it indexes 5,115 knowledge-base chunks |
| Embedding (all-MiniLM-L6-v2) | A small model that turns text into vectors so similar text can be found |
| spaCy PhraseMatcher | Rule-based matcher that finds listed skill phrases in resume text |
| ATS score | A lightweight, explainable resume score based on structure and keywords; not a real employer ATS |
| Scenario | A short workplace situation with decision questions and a final coding question |
| Level map | The game-style list of the 5 scenarios of a path; a level unlocks after passing the previous (70%+) |
| Code pool / variant | The set of coding problems for a scenario and the goal-specific versions of each |
| Hidden tests | Test cases whose inputs are never sent to the browser; only "a of b passed" is shown |
| Run / Submit | Run tests the code on all tests, repeatable, nothing locked; Submit locks the answer |
| OneCompiler | Third-party API that executes code in Python, C++, Java, JavaScript |
| XP / level / streak / badge | Gamification values, recomputed from activity, nothing stored |
| Placement readiness | A 0-100 score from roadmap, skill match, scenarios and streak; ready at 70 |
| CSRF | Attack where another site makes your browser send a request; blocked by a token on every state-changing request |
| BOOT_ID | A random value per server start; used to log everyone out after a restart in development |
| Smoke test | A script that exercises the app against a real database and checks results |
| Golden file | A saved expected output a test compares against |

## FAQ (honest answers)

**Why not let an LLM run the whole thing?** Correctness matters for scenarios, problems and roadmaps, and an LLM can be
wrong or inconsistent. Authored, reviewed, validated content is predictable and testable; the LLM is used for two small
personalisation and feedback tasks.

**How accurate is the career quiz?** Unknown. Its signals are hand-authored judgement. It is tested for consistency
(same answers give same result; opposite answers give opposite results) but has not been compared with real outcomes.
Ways to check are listed in file 04.

**Where do the readiness weights come from?** A design choice (25/35/30/10). They are not derived from data.

**Does the Goals page change my career match?** No. It tailors coding problems, starred scenarios and the roadmap note.

**Why can't I see the hidden test inputs?** So answers cannot be hard-coded to the tests. They stay on the server.

**Is user code run on your server?** No. It runs in OneCompiler. A local runner exists for development only and is not a
sandbox, so it must never be used on a server.

**What stops someone skipping a level?** The server checks that the previous scenario was passed and returns 403
`scenario_locked`; the browser cannot bypass it.

**Why no leaderboard?** Privacy, and an almost empty board in a demo.

**How do you prevent XP farming?** XP counts best scores and distinct achievements only.

**How is the password stored?** Hashed with bcrypt, never plain text.

**What happens to uploaded resumes and photos?** Resume text is analysed and results saved; profile pictures are re-encoded
to a small JPEG. (Retention policy for a deployed system is not defined, because it is not deployed.)

**Is it deployed?** No. It runs locally. Production settings exist but have never been run on a server.

**What are the main limitations?** See file 04: unvalidated quiz, no user study, C++/Java through OneCompiler not
confirmed, one weaker base roadmap, curated skill list, no deployment.

**What would you do next?** Check the quiz with a classmate survey and expert review, consider a chat-style quiz with
code-validated scoring (idea only), and deploy.

**Why is there no Skill DNA Map?** It was an early plan, replaced by scenarios and coding questions; the old tables were
dropped. The Master Document still mentions it and is out of date.
